## 1. The original goal

User pointed at one mis-rendered read in the bundled DRS validation suite
(`cat6_plus_1`, demo case for the 4-track alignment renderer): the read's 3'
soft-clip in the `pA-restore` BAM started with two `T` bases (`TT|AAAAAAAA...`)
that match the genome's homopolymer (`...ACTTGTT TT|ACCC...`). Those TT's were
body bases the old DRS pA trimmer ate. The strict trim policy is supposed to be:

> **ALWAYS stop at the first non-A in the tail. Only exception: a recognised
> adapter stub at the very 3' end (e.g. `...AAAAATC`).**

The current `trim-polya` code follows that policy. The bundled validation
parquet was generated by an older non-strict trimmer.

What started as "fix one over-trim" expanded into:

1. **Bundling empirical penalty + overhang tables into rectify** so `--Scer`
   auto-resolves them (no more out-of-tree paths on H2).
2. **Fixing the run-all subpackage** (broken relative imports + Module 2H
   wiring + tracker.write_manifest crash) so `rectify run-all --drs` works
   end-to-end with the canonical correct-first pipeline.
3. **Cross-platform sanity check** (H2 / Sherlock / M1) — all three produce
   identical TSVs from the same trimmed FASTQ.
4. **Validation bundle regeneration** — rerun the full pipeline on the raw
   Dorado source to produce a "current pipeline" bundle.

Step (4) is the open work. It's exposing real pipeline regressions, not just
position shifts.

## 6. Direction for the next agent — go path (A2): investigate every regression

**User decision (2026-05-17, after reviewing this handoff):**

> "Please direct the handoff agent to head in A2 direction and investigate
> all regressions."

This is the rigorous path. Each failing test is treated as a real pipeline
regression to root-cause, not as a value-update or xfail target. The
chimeric-junction fix we made this session (`bam_processor.py` short-circuit
omitting `junctions`/`n_junctions` for `Xz=1` reads) was found exactly this
way: a test failed, the root cause was a one-line bug, the fix recovered 5
tests at once. There are very likely 5–10 more bugs of similar shape hiding
behind the remaining 45 failures.

### How to work this

1. **Don't batch-update test expectations.** That defeats the purpose. If
   you find yourself wanting to change a number to make a test pass,
   stop — first find out why the pipeline produces the new number.
2. **Start with the highest-leverage failure cluster.** Cat3 5' rescue
   (8 failing tests across 4 reads) is one root cause: the consensus
   picks mapPacBio (no 5' soft-clip) instead of minimap2 (with the
   soft-clip that triggers rescue). One pipeline fix recovers 8 tests.
3. **Diff old bundle vs new bundle per read.** The pattern that
   recovered the chimeric-junction bug was: old bundle's read has
   property X, new bundle's read doesn't, why? Use
   `git show HEAD:rectify/data/validation/validation_reads.bam >
   /tmp/old.bam` to compare.
4. **Use the per-aligner BAMs.** Each read has 5 aligner alignments
   visible at `rectify/data/validation/aligners/`. When the consensus
   picks differently than the bundle, look at all 5 to see which
   should have won.
5. **One bug fix per commit.** Each fix to production code should land
   as its own commit with a descriptive message and the failing test
   it recovers.
6. **Add tests for each fixed bug.** If the existing validation test
   only catches the bug at the read level, add a unit test in
   `tests/test_<module>.py` for the specific code path. The chimeric
   junction fix didn't get a unit test — please add one as well.

The failures cluster around 5–6 distinct pipeline issues. Tackle them

#### Issue 1: Cat3 5' rescue doesn't fire (8 failing tests)

**Failing:**
- `TestCategory3JunctionRescue::test_5prime_exact_position[cat3_plus_1, cat3_minus_1]`
- `TestCategory3JunctionRescue::test_5prime_exon_cigar_set` (×4)

- Why does `consensus.py` / `chimeric_consensus.py` prefer mapPacBio over
