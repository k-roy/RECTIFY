# Pipeline order, chunking, scratch staging, run-all dispatcher

Hot rules for `rectify run-all` / `rectify split` / `rectify correct` on HPC.

---

## ⚠️ Chunking is mandatory for FASTQ inputs

**NEVER run `rectify run-all` on a FASTQ file without `--chunked-alignment`
(or use `rectify split`).** Enforced by a confirmation prompt in
`run_command.py` that requires typing `I UNDERSTAND THE RISKS`.
`--force-no-chunking` bypasses the prompt; do not use on HPC.

**Why:**
- BGZF BAM writes to Oak NFS: ~1 MB/min under concurrent load.
- `$SCRATCH` writes: ~75 GB/s — a **75,000× difference**.
- Whole-sample 2-hour alignment → **8 minutes** with 16 chunks on
  `$SCRATCH`.
- Whole-FASTQ inline alignment on HPC causes severe NFS contention that
  degrades performance cluster-wide.

**The ONLY correct way to process a FASTQ:**

```bash
# Short-read (QuantSeq / Illumina dT-primed):
rectify split reads.fastq.gz \
    --short-read --dT-primed-cDNA \
    -n 16 \
    --prefix sample_name --generate-slurm \
    --slurm-partition larsms,owners \
    --oak-output-dir /oak/.../sample_name/ \
    -o $SCRATCH/sample_name_chunks/
bash $SCRATCH/sample_name_chunks/submit_pipeline.sh

# Long-read (DRS / nanopore):
rectify run-all reads.fastq.gz --Scer --chunked-alignment \
    --slurm-partition larsms,owners \
    -o results/sample/
bash results/sample/submit_pipeline.sh
```

This policy is permanent and must not be relaxed.

## ⚠️ Pipeline order: correct-first is the ONLY validated approach

**The canonical, validated pipeline order is:
align → correct (per aligner) → merge corrected TSVs → consensus.**

Validated repeatedly on real DRS data (mini-1k sidecar, chunk003 preflight).
Do NOT implement or accept any "consensus-first" ordering.

### Correct order (VALIDATED)

```
rectify align → per-aligner BAMs
                    ↓ (for each aligner)
rectify correct --aligner-bams [all 5 BAMs] → per-aligner corrected_reads.tsv + corrected.bam
                    ↓
merge_corrected_tsvs(per-aligner TSVs) → merged corrected_reads.tsv (winning_aligner column)
                    ↓
build corrected_consensus.bam from winning-aligner corrected.bam per read
```

### WRONG order (DO NOT USE)

```
rectify align → per-aligner BAMs
    ↓
rectify consensus (on RAW BAMs) → consensus.bam   ← WRONG: selects winner before correction
    ↓
rectify correct (on consensus.bam only)            ← WRONG: single correction, no --aligner-bams
```

### Why correct-first matters

- **Aligner selection quality**: Winners are chosen based on CORRECTED 3' end positions, not raw alignment scores. Raw alignments are noisy; correction reveals which aligner found the true CPA.
- **Junction refinement (Module 2H)**: `--aligner-bams` feeds all 5 per-aligner BAMs to every correction run. Without it, Module 2H is disabled.
- **Win rates reflect biology**: deSALT 78.9%, mapPacBio 18.2%, uLTRA 2%, gapmm2 0.8%, minimap2 0.1% — these are from correct-first. Consensus-first gives different (worse) results.

### `split_command.py` pipeline order: FIXED (correct-first)

Implements correct-before-consensus order (fixed 2026-04-30). Old
`_merge_consensus_body()` that called `rectify consensus` on raw BAMs has
been removed. Current pipeline:

```
align arrays → run_merge_aligners.sh → run_prescan.sh
    → run_array_correct_{aligner}.sh (per aligner)
    → run_array_chunk_merge.sh → run_final_merge.sh
```

### Short-read support: `rectify split --short-read`

Pass `--short-read` to generate a simplified two-stage pipeline for
Illumina short reads (QuantSeq REV, dT-primed cDNA):

```bash
rectify split reads.fastq.gz \
    --short-read \
    --dT-primed-cDNA \
    -n 24 \
    -o $SCRATCH/sample_chunks/ \
    --genome genome.fa --annotation genes.gff \
    --oak-output-dir /oak/.../final_bams/ \
    --generate-slurm --slurm-partition larsms,owners

bash $SCRATCH/sample_chunks/submit_pipeline.sh
```

Generated scripts:
- `run_array_short_read.sh` (array 0..N-1): align (bbmap+bwa) → correct →
  consensus per chunk, all I/O on `$SCRATCH`.
- `run_final_merge_short_read.sh`: merge chunks → sort → index → copy to
  `--oak-output-dir` → clean up scratch.
- `submit_pipeline.sh`: chains both with `--dependency=afterok`.

**I/O policy in generated scripts:** chunk FASTQs and all intermediate
BAMs write to `$SCRATCH`. Only the final merged BAM is copied to Oak.

**Differences from long-read pipeline:**
- Aligners: `bbmap + bwa` instead of
  `mapPacBio/minimap2/gapmm2/uLTRA/deSALT`.
- No prescan step (no junction pool).
- `--dT-primed-cDNA` passed to all `rectify correct` calls — AG-mispriming
  module **is enabled** for short reads (genomic-context check downstream
  of 3' end).
- Two scripts instead of seven.

## ⚠️ Scratch staging: long-read array scripts need manual patching

**Scripts generated by `rectify split --generate-slurm` write alignment
outputs directly to `$OUTDIR` (Oak NFS) by default. This MUST be patched
before running at scale.**

100+ parallel array tasks writing BAMs to Oak NFS simultaneously causes
severe I/O contention. **Symptom**: jobs appear to run (CPU active) but
produce no output or accumulate very slowly. Bottleneck is Oak NFS, not
computation.

### The patch (apply to every generated array script)

```bash
# === ADD SCRATCH STAGING ===
# Replace direct $OUTDIR write:
#   CHUNK_OUTDIR="$OUTDIR/aligner_chunks/mapPacBio/chunk_${CHUNK_PAD}"
#   mkdir -p "$CHUNK_OUTDIR"
#   rectify align ... --output "$CHUNK_OUTDIR/..."
#
# With scratch-staging:
OAK_OUTDIR="$OUTDIR/aligner_chunks/mapPacBio/chunk_${CHUNK_PAD}"
mkdir -p "$OAK_OUTDIR"

SCRATCH_DIR="${SCRATCH}/rectify_mpb_${SLURM_JOB_ID}_${SLURM_ARRAY_TASK_ID}"
mkdir -p "$SCRATCH_DIR"
trap "rm -rf '$SCRATCH_DIR'" EXIT   # clean up even on failure

# ... run rectify align/correct to $SCRATCH_DIR ...

echo "Rsync scratch → Oak: $(date)"
rsync -a "$SCRATCH_DIR/" "$OAK_OUTDIR/"
# === END SCRATCH STAGING ===
```

Use suffix `rectify_mpb_` for `run_array_mapPacBio.sh` and
`rectify_${ALIGNER}_` for `run_array_others.sh`. Verify ALL `rectify
align` and `rectify correct` `--output` flags point to `$SCRATCH_DIR`,
not `$OAK_OUTDIR`.

### Scripts to patch after `rectify split --generate-slurm`

| Script | Rename | Scratch prefix |
|---|---|---|
| `run_array_mapPacBio.sh` | `CHUNK_OUTDIR` → `OAK_OUTDIR` | `rectify_mpb_` |
| `run_array_others.sh` | `CHUNK_OUTDIR` → `OAK_OUTDIR` | `rectify_${ALIGNER}_` |

**Long-term fix**: `split_command.py` should generate scratch-staging by
default for the long-read array scripts (as already done for short-read
via `--oak-output-dir`). Until that lands, always patch first.

## Architecture: `run-all` dispatcher

`rectify run-all` dispatches to `rectify/core/commands/run_command.py`,
which calls `_run_single_sample()` or `_run_multi_sample()` based on
whether `--manifest` is provided.

**DESeq2, motif discovery, and GO enrichment only run in multi-sample
mode.** Single-sample runs skip them by design
(`run_deseq2 = n_samples > 1`).

### DRS workflow: `--drs` flag

For Dorado direct RNA-seq BAMs, pass `--drs` to `run-all`:

```bash
rectify run-all sample_dorado.bam --drs --Scer -o results/sample/
```

Inserts two DRS-specific steps around the standard pipeline:

| Step | Action | Implementation |
|---|---|---|
| **0** | Poly(A)+adapter pre-trimming | `trim_drs_bam_polya()` → `samtools fastq -T pt` |
| 1 | Multi-aligner alignment | normal, on trimmed FASTQ |
| 2 | Correction | normal |
| 3 | Analysis | normal |
| **4** | Restore poly(A) as soft-clips | `restore_polya_softclips()` |

**Key implementation details:**
- DRS Steps 0 and 4 run in **both** single-sample (`_run_single_sample`)
  and multi-sample manifest (`_process_one_sample`) paths.
- Single-sample: trimmed FASTQ → `$SCRATCH/drs_trim/`; trim metadata
  parquet → Oak output dir (persistent, needed for Step 4).
- Multi-sample: trimmed FASTQ + temp BAM → `<sample_output>/drs_trim/`;
  metadata parquet → `<sample_output>/`.
- `--drs` has no effect on FASTQ inputs (assumed already trimmed).
- `softclipped_bam` path for Step 4 is inferred from the trimmed FASTQ
  stem (stripping `_trimmed`/`.fastq`/`.gz`):
  `{stem}.rectified_pA_tail_trimmed.bam`.
- Single-sample Steps 0 and 4 are recorded in the provenance tracker as
  `drs_trim` and `drs_restore`.
- Multi-sample Step 4 restore is non-fatal: failure is logged but the
  sample still returns success.

### DRS FASTQ generation: do NOT use `samtools fastq -T pt`

`samtools fastq -T pt` embeds the poly-A tag as a tab-separated suffix in
the FASTQ header: `@UUID\tpt:i:25`. mapPacBio reads the entire header
verbatim and writes `UUID_pt:i:25` as the BAM QNAME after `samtools
sort`. This creates duplicate read IDs (`UUID_pt:i:0` and
`UUID_pt:i:13`) and breaks parquet lookups keyed by bare UUID.

**Fix (implemented in `run_command.py`):** call `samtools fastq` without
`-T pt`. Poly-A lengths are stored in the parquet trim metadata. The
FASTQ read name must always be the bare UUID.

Note: `preprocess.py:align_dorado_bam_to_genome()` uses `samtools fastq
-T '*' | minimap2 -y` — a different code path that pipes directly into
minimap2 without writing a FASTQ, so tags go into minimap2 aux fields
(not the read name) and are safe.

## HPC I/O: always stage through $SCRATCH

NFS-backed shared storage under concurrent load inflates wall time 2–3×.
`$SCRATCH` is high-bandwidth node-local storage.

### Pattern (Python pipeline)

`run_command._run_single_sample()` handles this automatically:

```python
from rectify.slurm import make_job_scratch_dir, sync_outputs

scratch = make_job_scratch_dir('rectify_single')  # None if no scratch
work_dir = scratch if scratch else output_dir

# ... all alignment + correction + analysis writes to work_dir ...

if scratch:
    sync_outputs(scratch, output_dir)  # rsync everything back
    shutil.rmtree(scratch)
```

### Pattern (generated SLURM scripts)

`batch_command.generate_slurm_scripts()` inserts staging blocks when
`use_scratch=True` in the profile (default in `hpc_cpu.yaml`):

- BAM inputs are `cp`'d to `$SCRATCH` before `rectify correct`.
- FASTQ inputs are left on the source filesystem (read sequentially
  once, no benefit to staging).
- All outputs are `rsync`'d back to the output directory after
  correction.

### `$SCRATCH` caveats

- Auto-purged after **90 days** on most HPC clusters — final outputs must
  land on persistent storage.
- Not shared across nodes — do not use `$L_SCRATCH` for multi-node jobs.
- `make_job_scratch_dir()` priority: `$SCRATCH` → `$SLURM_TMPDIR` →
  `$TMPDIR`.

## Memory: use `--streaming` for large BAMs

`rectify correct` without `--streaming` loads all reads into RAM. The
default parallel path (`process_bam_file_parallel`) accumulates all
results before writing. For a 7 GB BAM with 40M reads this requires
~30–40 GB RAM.

With `--streaming` (`process_bam_streaming`), reads are processed and
written one chunk at a time (default 10,000 reads/chunk). Peak RSS drops
to ~4–5 GB regardless of BAM size.

**Always use `--streaming` in SLURM jobs.** `hpc_cpu.yaml` sets
`streaming: true` by default.

## Thread limits: set before importing numpy

**SLURM will ban accounts that spawn more processes than allocated
CPUs.** `set_thread_limits()` in `slurm.py` must be called before any
import of numpy, sklearn, or pydeseq2. These libraries auto-spawn threads
via OpenMP, OpenBLAS, MKL, and joblib's loky backend.

The loky backend (used by sklearn/pydeseq2) ignores `JOBLIB_WORKERS` —
you **must** set `LOKY_MAX_CPU_COUNT`.

```bash
# In SLURM scripts — set BEFORE running Python
export OMP_NUM_THREADS=$SLURM_CPUS_PER_TASK
export OPENBLAS_NUM_THREADS=$SLURM_CPUS_PER_TASK
export MKL_NUM_THREADS=$SLURM_CPUS_PER_TASK
export LOKY_MAX_CPU_COUNT=$SLURM_CPUS_PER_TASK   # critical for pydeseq2
```
